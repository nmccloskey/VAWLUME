# Agreement query views

Phase 1.9 makes persisted arbitrary-N agreement practical to query without
adding summary columns to the authority tables. The storage contract remains
unchanged:

- agreement_group_members identifies represented native detections;
- agreement_supporting_edges cites every exact candidate_pair_id;
- source analyses and their declared extraction inputs identify which pairwise
  comparisons were assessed.

Counts, fractions, patterns, and status flags below are ordinary SQLite views.
They cannot drift independently from the member and edge rows they summarize.

## Long-form members

v_agreement_group_members returns one row per native detection in an agreement
group. It carries group/run/recording identity, native detection identity,
extraction run and extractor/version identity, and native start/end geometry
with derived duration. It does not collapse multiple detections from one
extractor.

## Exact support edges

v_agreement_supporting_edges returns one row per stored support edge. Its row
count and candidate_pair_id set therefore match agreement_supporting_edges
exactly.

The view retains:

- agreement group/run/recording identity;
- supporting-edge id and exact candidate-pair id;
- source pairwise analysis id/key;
- both detection, extraction-run, extractor/version, and native-event identities;
- every pairwise temporal evidence field and candidate status/details;
- source match-group id, match type, and ambiguity status where derivable.

pairwise_topology_label is no_group_materialized when the source analysis has
candidate rows but no groups. The underlying topology columns remain NULL:
absence is reported, not converted into ambiguity.

Candidate endpoint order remains visible in detection_a_id and detection_b_id.
Display-only keys have a separate deterministic orientation:

    extractor_pair_key = lower extractor_key -- higher extractor_key
    detection_edge_key = lower run_key#native_event_id -- higher selector

No transitive detection edge is generated by either key.

## Possible and supported extractor pairs

v_agreement_extractor_pair_support returns one row for every unordered pair of
extractors represented in a group. The pair is ordered by extractor_key, and
the view includes both extractor/run/version endpoints.

source_analysis_count, source_analysis_run_id/key, and is_assessed expose
whether the agreement run declared a source analysis covering those two
extraction runs. Phase 1 requires exactly one source for every participating
pair; keeping the count visible makes that contract auditable.

support_edge_count and is_supported are a coarse reduction only. An unsupported
row remains present with a zero count, which names the missing pair instead of
reporting only that one pair is absent. Exact detection edges remain in
v_agreement_supporting_edges.

## Group summary

v_agreement_group_summary returns one row per agreement group:

| Dimension | Columns |
|---|---|
| represented observations | member_count, extraction_run_count, extractor_count |
| represented identities | extractor_set_key/label, extraction_run_set_key |
| exact support | support_edge_count |
| coarse support | supported/possible extractor-pair counts, support_fraction |
| assessment coverage | assessed_extractor_pair_count, is_pairwise_assessment_complete |
| exact pair patterns | supported/unsupported extractor-pair pattern and label columns |
| independent shape facts | pair completeness, one-detection-per-extractor, clean one-to-one |
| topology | pairwise and ambiguous topology patterns |
| uniqueness | is_singleton, is_extractor_unique |

For N represented extractors, possible_extractor_pair_count is the row count in
the possible-pair view and therefore equals N*(N-1)/2. support_fraction is the
supported count divided by that possible count. It is NULL for a singleton
because no extractor pair is possible. Pair-support and assessment-completeness
flags are false there rather than vacuously reporting corroboration.

is_unambiguous_one_to_one requires at least one exact edge and requires every
contributing source group to report both one_to_one and unambiguous. A
candidate-only source, ambiguous split, or singleton therefore does not receive
that label.

## Pattern convention

Machine-facing patterns use stable extractor_key values:

    deepsqueak--mupet|deepsqueak--usvseg

Within each pair, keys are lexical ascending; pairs are then lexical ascending
and joined by a vertical bar. Human-facing labels use extractor names, spaced
double hyphens within a pair, and semicolons between pairs. Empty supported or
unsupported sets are empty text. Patterns are display/query keys, never primary
identity.

## Shape examples

| Shape | K / possible | One detection per extractor | All sources clean 1:1 |
|---|---:|---:|---:|
| clean triangle | 3 / 3 | yes | yes |
| strict-spec open chain | 2 / 3 | yes | yes |
| pair only | 1 / 1 | yes | yes |
| singleton | 0 / 0, fraction NULL | yes | no |
| complete split/merge | 3 / 3 | no | no |

The open chain exposes deepsqueak--mupet as its exact unsupported pair. The
split/merge group retains six exact detection edges while reducing to three
supported extractor pairs. A separate four-extractor query test produces six
possible pairs, proving arbitrary-N combinatorics rather than a fixed
three-extractor rule.

## Example queries

Find partial groups and name their missing pairs:

    SELECT agreement_run_key, group_key,
           supported_extractor_pair_count, possible_extractor_pair_count,
           unsupported_extractor_pair_pattern
    FROM v_agreement_group_summary
    WHERE is_pairwise_assessment_complete = 1
      AND is_extractor_pair_support_complete = 0
      AND is_singleton = 0;

Inspect every exact edge behind one coarse extractor-pair row:

    SELECT candidate_pair_id, detection_edge_key, temporal_iou,
           source_analysis_run_key, pairwise_topology_label
    FROM v_agreement_supporting_edges
    WHERE agreement_group_id = ?
      AND extractor_pair_key = ?
    ORDER BY candidate_pair_id;
