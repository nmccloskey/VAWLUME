# VAWLUME Schema

This directory holds VAWLUME's relational model. Two files describe it, and only
one of them is authoritative.

| File | Status |
|---|---|
| [`schema.sql`](schema.sql) | **Authoritative.** Hand-maintained, and what VAWLUME executes to create a database |
| [`schema.json`](schema.json) | **Generated.** A machine-readable export of `schema.sql`, never hand-edited |
| [`fixtures/`](fixtures/) | Deterministic synthetic-fixture and acceptance-query sources used by the tests |

## `schema.sql` is the schema

VAWLUME is SQLite-backed, and this file is the model. Every table, view,
trigger, index, and constraint a VAWLUME database has comes from here, applied
through `vawlume.db.applySchema`. It carries its own version in its header, in
the `schema_info` seed, and in `PRAGMA user_version`; all three must agree, and
a check enforces that.

If the model needs to change, this is the file that changes.

## `schema.json` is a representation of it

`schema.json` is generated by [`tools/schema_documentation.m`](../tools/schema_documentation.m),
which builds a clean throwaway SQLite database from `schema.sql`, exports it
with tbls, verifies that the export accounts for every object the database
actually has, and writes the result here. It is committed so the model can be
read — and rendered as a diagram — without a database and without the toolchain
that produced it.

**Never hand-edit it.** If the generated file is wrong, the generator is wrong.

```matlab
addpath("tools"); schema_documentation                 % regenerate
addpath("tools"); schema_documentation(Mode="check")   % verify it is current
```

The check rebuilds the export from `schema.sql` and compares byte for byte, so
the two files cannot drift apart unnoticed. When they have drifted it names what
changed — which objects were added, removed, or redefined — rather than only
reporting that the files differ. The obligation to run it lives in
[`docs/development/02_development_workflow.md`](../docs/development/02_development_workflow.md).

tbls is a development dependency. No VAWLUME runtime path calls it, and an
ordinary user analyzing data never needs it installed.

### Two things a reader will notice in the file

**`"name": "vawlume.sqlite"` at the top** is the disposable temporary database
the generator builds and deletes. That filename is fixed deliberately: tbls
records it in the export, so a varying name would change the artifact on every
run and force a canonicalization step — and anything that rewrote the export
would make `schema.json` a second hand-maintained representation of the schema.
Fixing the name is what makes the file reproducible without one.

**`driver.database_version`** is the SQLite version bundled inside the tbls
binary. It is not VAWLUME's, not MATLAB's, and not the schema's. It is left
exactly as tbls reports it, so a tbls upgrade shows up as an honest one-line
diff instead of being hidden — a diff that is only that line is not a schema
change.

## Exploring the model as a diagram

**[Explore the VAWLUME database schema interactively](https://liambx.com/erd/p/github.com/nmccloskey/VAWLUME/blob/main/schema/schema.json?format=tbls)**

[Liam ERD](https://liambx.com) renders a tbls export as an interactive
entity-relationship diagram in the browser — pan, zoom, search for a table, and
follow its foreign keys — directly from `schema.json` on GitHub, with nothing to
install. Like tbls, it is a documentation dependency and never a runtime one.

The link reads `schema.json` from `main`. Any pushed branch or tag can be
substituted in the URL to explore the schema as it stood there.

### What the ERD does not show

`schema.json` itself is a faithful export rather than a summary: every table,
view, trigger, index, and CHECK constraint in the schema is present in it, each
with its full SQL. Nothing is dropped on the way out of the database.

What a diagram communicates is narrower than what the file contains. An ERD
shows tables, their columns, and the foreign keys between them. That is the
right picture for finding your way around the model, and it is not the whole
model. In particular it does not convey:

- **triggers.** VAWLUME uses them for cross-table invariants SQLite cannot
  express as CHECK constraints — the rules that keep provenance, lineage, and
  declared semantics consistent across tables. They are some of the most
  load-bearing logic in the schema and none of it is a line between two boxes.
- **CHECK constraints.** Much of what makes a column *meaningful* rather than
  merely typed is a CHECK — for example that a score may be null, but a score
  without its declared semantics may not.
- **views.** The query surface the schema defines over its own tables.
- **why any of it is shaped this way.** The design contracts under
  [`docs/design/`](../docs/design/) and the data dictionaries under
  [`docs/development/`](../docs/development/) carry that, and the ERD is not a
  substitute for them.

A reader who took the ERD for the whole model would miss the rules that make it
correct. Use it to navigate; read [`schema.sql`](schema.sql) to understand.
